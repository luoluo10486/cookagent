# 工具注册与执行链路说明

本文说明当前正式工具、注册表查看入口和一次工具调用如何从 Agent Runtime 进入 Java 控制面。数据库清理脚本属于本地维护能力，不注册为 Agent 工具，也不会接受模型调用。

## 1. 当前正式工具

| 工具 | 作用 | 执行边界 | 是否写业务数据 | 是否需要确认 |
|---|---|---|---|---|
| `calculator` | 执行受限的数值表达式和克重计算 | Python 提案，Java `ToolGatewayServiceImpl.executeCalculator` 执行 | 否 | 否 |
| `time_parser` | 将“今天、昨天、最近 7 天”等问题解析为带时区的时间范围 | Python 提案，Java `executeTimeParser` 执行 | 否 | 否 |
| `knowledge_search` | 检索公共、已发布知识片段并生成引用 | Runtime 检索，Java 负责 Run 授权范围；不是 Java SQL/写入 Adapter | 否 | 否 |
| `database_query` | 查询当前用户范围内的饮食、计划、营养和购物数据 | Python SQL Planner 提案，Java Schema Catalog、AST Guard 和只读执行器执行 | 否 | 否 |
| `food_log_writer` | 创建、修改、删除、恢复饮食记录 | Python 提案，Java Approval 和 FoodLog 用例执行 | 是 | 是 |
| `plan_validator` | 校验餐食计划的结构、营养和业务约束 | Python 提案，Java 规则执行器执行 | 否 | 否 |
| `meal_plan.save_plan` | 保存已校验的餐食计划并生成购物清单 | Python 提案，Java Approval 和 MealPlan 用例执行 | 是 | 是 |

营养目录的 `POST /foodmate/internal/v1/nutrition/search` 是 Runtime 的独立候选检索入口。它查询 Milvus 营养集合，返回 `nutrition_food_id` 候选；饮食记录真正写入时仍由 Java 回源 PostgreSQL 获取营养值和单位换算。它当前不作为可以直接写库的 Agent Tool 注册。

## 2. 注册表查看位置

注册元数据只有 PostgreSQL 和版本化代码种子两个来源：

1. 管理端进入“管理后台 -> 工具 -> 工具注册表”，查看名称、版本、风险、权限、超时、重试和幂等策略。
2. 调用只读接口 `GET /api/admin/tools/registry`，返回当前未删除工具和当前 Schema。
3. 直接查询 PostgreSQL：

```sql
SELECT t.name,t.status,t.current_version,s.version,s.timeout_ms,
       s.retryable,s.idempotent,s.permissions
FROM tool_registries t
JOIN tool_schema_versions s
  ON s.tool_id=t.tool_id
 AND s.version=t.current_version
 AND s.is_deleted=FALSE
WHERE t.is_deleted=FALSE
ORDER BY t.name;
```

正式初始目录见 `script/sql/FoodMate/migration/V18__m2_2_tool_registry_seed.sql`；Java 本地 stub 的契约镜像见 `foodmate-application/src/main/java/com/foodmate/application/runtime/service/ToolRegistryCatalog.java`。

## 3. 一次调用如何执行

以 `database_query` 为例：

```text
用户问题
  -> Python Router / SQL Planner
  -> V1ToolProposal
  -> Java Tool Gateway
  -> Tool Registry 当前版本解析
  -> ToolPolicy 输入、权限和确认策略
  -> Schema Catalog + JSqlParser AST + 只读/LIMIT/用户范围 Guard
  -> PostgreSQL 执行
  -> SQL Query Audit + ToolCall Fact
  -> V1ToolResult
  -> Python Composer
  -> run.completed / SSE
```

写工具的区别是 Java 在 Tool Gateway 中先校验 Proposal、Run/用户归属、确认事实和幂等键，再调用既有业务用例；成功只在 PostgreSQL 事务提交后返回。相同 Proposal 重放返回已有事实，不重复写入。

## 4. 在哪里看“具体执行了什么”

- AgentRun 页面中的工具轨迹：看工具名、状态、耗时、错误码和终态事件。
- `tool_calls`：看每次工具的安全输入摘要、输出摘要、状态、耗时和错误码；不保存完整 Prompt、密码、令牌或完整业务请求。
- `operation_audits`：看统一操作动作、结果、目标和关联 ID。
- `sql_query_audits`：只对 `database_query` 查看解析后的问题、受控 SQL 审计状态、行数和延迟；SQL 语句仍受既有脱敏和权限边界约束。
- Java 具体分派代码：`foodmate-application/.../ToolGatewayServiceImpl.java`。
- Python 提案和工作流代码：`agent-runtime/agent_core.py`、`agent-runtime/proposal_protocol.py`、`agent-runtime/sql_planner.py`。

## 5. 本地数据清理入口

工具注册表的清理只删除无引用的 `e2e_tool_*` 残留：

```powershell
.\script\sql\FoodMate\maintenance\cleanup-local-tool-registry.ps1
.\script\sql\FoodMate\maintenance\cleanup-local-tool-registry.ps1 -Execute -Confirmation CLEAN_LOCAL_TOOL_REGISTRY
```

本地业务基线重建会保留用户账户、营养目录、单位换算、SQL Catalog、模型配置和正式工具，只清理会话、消息、AgentRun、知识导入、饮食记录、餐食计划及其技术事实；执行前自动生成 PostgreSQL 备份：

```powershell
.\script\sql\FoodMate\maintenance\reset-local-business-data.ps1
.\script\sql\FoodMate\maintenance\reset-local-business-data.ps1 -Execute -RebuildReferenceData -Confirmation RESET_LOCAL_BUSINESS_DATA
```

默认 dry-run 不改库。`-RebuildReferenceData` 会幂等重放 V18 工具种子和 V33 USDA 目录种子并执行 V33 validation；不会清理 Milvus 向量，向量清理或重建必须单独执行并记录。

公共 RAG 外部索引清理是独立维护操作，只在 PostgreSQL 没有活动知识文档和切片时允许执行。脚本只清理当前公共知识集合、明确命名的 `codex` 测试集合和 stub 的 `:chunks` 哈希；营养集合 `foodmate_nutrition_foods` 只读核对，不会被清理：

```powershell
.\script\sql\FoodMate\maintenance\cleanup-local-rag-indexes.ps1
.\script\sql\FoodMate\maintenance\cleanup-local-rag-indexes.ps1 -Execute -Confirmation CLEAN_LOCAL_RAG_INDEXES
```

该脚本不会删除 PostgreSQL 业务表、Milvus 集合定义、营养向量或 Worker 完成事实。工具注册清理、本地业务数据清理和 RAG 外部索引清理互相独立，执行结果都应追加到 `script/sql/FoodMate/EXECUTION_RECORD.md`。
