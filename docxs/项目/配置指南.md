# FoodMate 配置指南

> 当前阶段（2026-09-05）：`local-stub`/`local` 是当前开发重点；`dev`/`prod` 只保留配置契约和后置目标，不代表已建立隔离环境。M2-1 的 stub、local deterministic 和 local OpenAI-compatible 配置已经进入代码；Docker Runtime 启动、readiness、SiliconFlow Chat/Embedding 协议和 R1-R4 真实业务入口均已有一次性证据；真实云长稳、完整生产监控、成本对账和部署仍后置。

## 1. 配置分层与现状

配置事实以 `foodmate-bootstrap/src/main/resources/application*.yml`、`agent-runtime` 当前代码、`docker/.env.example` 和 `docker/compose.yml` 为准。M1-3 HTTP Service JWT、M1-4 RocketMQ/Redis 传输、固定 Workflow、Eval Gate、模型适配器、checkpoint、Proposal/Result、M2-1 公共知识库 RAG、M2-2 Tool/SQL 和 M2-3 管理核心切片已进入代码并完成业务验证；2026-09-05 已取得 SiliconFlow Chat/Embedding 协议和 R1-R4 真实业务入口的一次性证据。Docker 启动、readiness 和配置契约已验证，但云服务长稳、生产级指标/治理和跨环境部署仍未完成。配置名出现在设计文档中不等于已有可用配置项。

Secret 只能从环境变量或受控 Secret 挂载注入。不要在 Markdown、YAML 默认值、提交记录、终端输出或日志中写入真实密钥、JWT、私钥、数据库密码或模型请求体。

## 2. 当前 Java YAML

| 文件 | 用途 | 当前事实 |
|---|---|---|
| `application.yml` | 公共默认配置 | 服务名 `foodmate`、端口 `8080`、Actuator 暴露 `health,info`、UTC Jackson、MyBatis-Plus、旧 AI 相关键和 `local-stub` 默认 profile |
| `application-local-stub.yml` | 无数据库本地骨架 | 排除 DataSource/Flyway 自动配置，`foodmate.runtime.stub-enabled=true` |
| `application-local.yml` | 本机 PostgreSQL | `DB_URL`、`DB_USERNAME`、`DB_PASSWORD` 可覆盖的 datasource，Flyway 默认关闭，stub 关闭 |
| `application-dev.yml` | 开发环境 PostgreSQL | 必须提供 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD`，Flyway 默认关闭，stub 关闭 |
| `application-prod.yml` | 生产 PostgreSQL | 必须提供 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD`，Flyway 默认关闭，stub 关闭 |

`local` 中现有默认 URL 是 `jdbc:postgresql://localhost:5432/FoodMate`，默认用户名和密码是 `postgres`。这组值用于本机 Docker PostgreSQL 验证，不应复制为共享环境或生产凭据。`dev` 与 `prod` 没有默认值，缺失环境变量时应让启动失败而不是用猜测的连接信息继续运行；`prod` 还会拒绝 `postgres/postgres` 这组默认凭据。

所有环境均禁止应用启动自动执行建表、迁移或回滚。数据库脚本必须由人工按 `script/sql/FoodMate` 中的执行记录、校验 SQL 和备份/回滚要求执行；Flyway 依赖仅保留给显式测试和脚本验收使用。

## 3. 当前旧 AI 配置，待迁移

`application.yml` 仍包含下列旧职责配置：

- `foodmate.model`：默认聊天和嵌入模型、调用超时。
- `foodmate.gateway`：`base-url` 和 `MODEL_GATEWAY_KEY`。
- `foodmate.rag`：`top-k`、`rerank-top-n`、`collection`。
- `foodmate.milvus`：host、port 和 `MILVUS_TOKEN`。

这些键仍是现有 Java YAML 的静态事实；M2-1 的实际 RAG 运行配置位于 Runtime 环境变量，Java 只负责授权范围、结果回写和对外 API。当前已有 M1-3 HTTP Runtime Client、M1-4 RocketMQ transport、Redis Inbox/Outbox、固定 Workflow、Eval、真实云适配器、M2-1 RAG 和 Java 事件消费；2026-09-05 的 Chat/Embedding 真实协议和 R1-R4 业务证据已记录，但长稳、成本对账和完整生产治理仍未完成。不得把旧目标键解释为当前唯一配置来源；Java 控制面与 Python Runtime 仍分别接管各自职责。

## 4. Java HTTP Runtime 兼容配置
已批准的 Java Runtime Client 蓝图使用 `foodmate.agent-runtime` 前缀，替代旧 model gateway 语义。目标配置至少包括：

| 配置类别 | 目标项 | 约束 |
|---|---|---|
| Runtime 连接 | `base-url`、`contract-version`、connect/read/run timeout、重试上限与退避 | 生产地址必须为内部 HTTPS；版本固定 `v1`；任一 timeout 不得超过绝对 `deadline_at` |
| Java 到 Python 身份 | JWT issuer、audience、key id、TTL、私钥引用 | audience 固定为 `foodmate-agent-runtime`；短期 JWT；TTL 不得超过 300 秒；私钥只从 Secret 挂载或环境引用读取 |
| Python 到 Java 身份 | 反向 Service JWT 的 issuer、audience、scope、key id 与公钥引用 | Python 事件、ToolProposal 和 SqlProposal 必须经过 Java 验证；JWT 不替代 Java 的业务授权 |
| 契约与可观测性 | `X-Contract-Version`、request/trace 标识与脱敏日志 | 所有 ID 是字符串，时间是 UTC RFC 3339；禁止记录 JWT、私钥、完整 Prompt 或原始请求体 |

M1-3 已实现双向 Ed25519 Service JWT 的实际配置与签发/校验；表中部分最终命名、轮换和 HTTPS 仍待完善。M1-4 RocketMQ 消息体不携带 Service JWT，HTTP 认证配置只服务兼容/测试适配。不得复制示例私钥或将静态 Bearer token 写入配置。

### 4.1 Java 侧 RocketMQ 配置（M1-4 阶段 D 已实现）

`application.yml` 的 `foodmate.runtime` 下已落地下列键，环境变量名与 §5.9 保持一致：

| YAML 键 | 环境变量 | 默认值 | 说明 |
|---|---|---|---|
| `transport` | `FOODMATE_AGENT_TRANSPORT` | `http` | `http` 是 M1-3 兼容通道，`rocketmq` 是正式主通道；两者互斥 |
| `rocketmq.name-server` | `FOODMATE_ROCKETMQ_NAMESRV_ADDR` | `localhost:9876` | 本地单 NameServer |
| `rocketmq.command-topic` | `FOODMATE_ROCKETMQ_TOPIC_AGENT_COMMAND` | `foodmate-agent-command-v1` | Java -> Python |
| `rocketmq.event-topic` | `FOODMATE_ROCKETMQ_TOPIC_AGENT_EVENT` | `foodmate-agent-event-v1` | Python -> Java |
| `rocketmq.proposal-topic` | `FOODMATE_ROCKETMQ_TOPIC_AGENT_PROPOSAL` | `foodmate-agent-proposal-v1` | 阶段 D 只建 Topic，尚无消费者 |
| `rocketmq.result-topic` | `FOODMATE_ROCKETMQ_TOPIC_AGENT_RESULT` | `foodmate-agent-result-v1` | 同上 |
| `rocketmq.java-event-consumer-group` | `FOODMATE_ROCKETMQ_CONSUMER_GROUP_JAVA_AGENT_EVENT` | `foodmate-java-agent-event-v1` | 顺序消费 RunEvent |
| `rocketmq.producer-group` | `FOODMATE_ROCKETMQ_PRODUCER_GROUP_JAVA` | `foodmate-java-agent-command-producer-v1` | 命令发布者 |
| `rocketmq.send-timeout-ms` | `FOODMATE_ROCKETMQ_SEND_TIMEOUT_MS` | `3000` | 等待 Broker 确认上限 |
| `rocketmq.consumer-max-retries` | `FOODMATE_ROCKETMQ_CONSUMER_MAX_RETRIES` | `8` | 超出后进入该消费组 DLQ |

`transport=rocketmq` 时 HTTP 的 `V1RuntimeClient` bean 不再装配，由 `RuntimeRocketMqConfiguration` 提供唯一实现，从装配层面保证规则 10（同一进程不能同时启用两条业务派发通道）。Topic 与 consumer group 命名在 `RocketMqSettings` 构造时校验，非法值直接让 Spring 装配失败。

本地 Broker 关闭了 `autoCreateSubscriptionGroup`，消费组必须由 `docker/rocketmq/init-topics.sh` 预建；其中 `foodmate-selftest-v1` 专供自动化测试使用，避免测试挪动正式消费组的位点。

## 5. Python 模型、RAG 与治理配置

Python Runtime 当前已落地 M1-4 的固定 Workflow、模型适配、Eval、预算、checkpoint 和 M2-1 公共知识库 RAG。RAG 支持 `stub`、`local + deterministic`、`local + openai-compatible` 三种明确组合：stub 只使用共享 Redis 关键词索引；local deterministic 写入 Milvus 但不产生外部费用；local openai-compatible 才读取显式 embedding endpoint、API Key 和 model。真实模式缺少配置时失败关闭，不会回退到 stub。模型 API key、向量检索凭据和任何 RAG 存储凭据必须通过 Runtime 的 Secret 引用传入。Python 源码入口从仓库 `.env` 默认只加载非敏感配置；API Key、密码、Token 和私钥必须来自当前进程。需要文件密钥的隔离实验必须在进程中显式设置 `FOODMATE_RUNTIME_ALLOW_DOTENV_SECRETS=true`，不能由 `.env` 自身开启。

Python 不应获得 PostgreSQL 业务库 URL、用户名或密码，也不应直接复用 Java 的 Tool/SQL 执行凭据。Java 只向 Python 传递经授权的 `authorized_context`、Runtime 选项和 V1 契约消息；Python 的 Tool/SQL 请求必须以 proposal 回到 Java。

Python probe 路由固定为 `GET /foodmate/internal/health/live` 与 `GET /foodmate/internal/health/ready`，所有调用保留完整的 `/foodmate/internal` 前缀。当前 readiness 已报告 checkpoint backend、Redis、RocketMQ producer/consumer 和进程内 Eval 统计；Redis AOF 是否启用仍属于部署配置，不能仅凭 readiness 的业务状态字段推断。

### 5.1 Workflow 预算环境变量

以下变量定义 Python Workflow 的运行上限。默认 deterministic provider 和本地 RAG 会消费对应运行配置；写入环境文件仍不代表真实云服务或生产治理已经启用。

| 环境变量 | 默认值 | 配置语义 |
|---|---:|---|
| `FOODMATE_AGENT_MAX_STEP_RETRIES` | `2` | 单步骤可重试次数 |
| `FOODMATE_AGENT_MAX_REPLANS` | `1` | 单 Run 可重新规划次数 |
| `FOODMATE_AGENT_MAX_ANSWER_REWRITES` | `1` | 单 Run 可重写最终答案次数 |
| `FOODMATE_AGENT_MAX_TOTAL_STEPS` | `30` | 单 Run Workflow 节点推进总预算 |
| `FOODMATE_AGENT_MAX_MODEL_CALLS` | `12` | 单 Run 逻辑模型调用总预算 |

带注释的默认配置示例：

```dotenv
# 单个 Workflow 步骤失败后，最多允许额外重试 2 次。
# 不包含第一次正常执行；设为 0 表示步骤失败后不自动重试。
FOODMATE_AGENT_MAX_STEP_RETRIES=2

# 一次 AgentRun 最多允许重新生成执行计划 1 次。
# 初始规划不计入该值；设为 0 表示执行后不允许重新规划。
FOODMATE_AGENT_MAX_REPLANS=1

# Final Eval 判定答案仅存在表达、格式或轻微遗漏问题时，最多重写 1 次。
# 首次生成候选答案不计入该值；设为 0 表示 Eval 不触发答案重写。
FOODMATE_AGENT_MAX_ANSWER_REWRITES=1

# 一次 AgentRun 最多推进 30 个 Workflow 节点。
# Router、Planner、执行、校验、反思、Composer、Eval 等每次进入节点都计数，
# 用于阻止节点之间无限循环；该值必须大于 0。
FOODMATE_AGENT_MAX_TOTAL_STEPS=30

# 一次 AgentRun 最多发起 12 次逻辑模型调用。
# Router、Planner、Composer、LLM Eval 等调用都计入；同一逻辑调用的供应商
# 网络重试不重复计数，而是由独立的 provider attempt 策略控制；该值必须大于 0。
FOODMATE_AGENT_MAX_MODEL_CALLS=12
```

示例中的 `2/1/1/30/12` 是默认建议值，不是不可修改的常量。调大预算会提高复杂任务完成空间，同时增加延迟、Token 成本和循环风险；调小预算会更快失败或降级。生产环境应结合离线 Eval、运行耗时和成本数据调整，不能只因为任务偶尔失败就无上限调大。

### 5.2 并发与队列

```dotenv
# 同一用户最多允许 2 个活跃 Session（由 Redis admission 的 user ZSET 协调）。
# 不限制用户创建或保存的 Session 总数。
FOODMATE_AGENT_MAX_ACTIVE_RUNS_PER_USER=2

# 整个 Runtime 最多允许 20 个 AgentRun 同时执行。
FOODMATE_AGENT_MAX_ACTIVE_RUNS_GLOBAL=20

# 全局等待队列最多保存 100 个 Run；队列已满时返回 RUNTIME_CAPACITY_EXCEEDED。
FOODMATE_AGENT_MAX_QUEUED_RUNS_GLOBAL=100

# Redis permit 租期，单位秒；执行期间由当前 owner token 受控续租。
FOODMATE_AGENT_PERMIT_LEASE_SECONDS=180

# 当前本地实现使用 priority + 时间排序；priority burst/aging 参数保留为后续公平性增强扩展。
```

同一 Session 最多一个 active Run 是 PostgreSQL 一致性规则，不提供关闭开关。`FOODMATE_AGENT_ADMISSION_ENABLED=true` 时 Redis 不可用不降级为进程内业务并发计数，新 Agent 请求返回 503 和 `RUNTIME_COORDINATION_UNAVAILABLE`。

### 5.3 四类超时

```dotenv
# Run 在 Java 队列中最长等待 30 秒。
FOODMATE_AGENT_QUEUE_TIMEOUT_SECONDS=30

# Run 真正开始执行后的总时限，默认 120 秒；不包含 waiting_user 时间。
FOODMATE_AGENT_EXECUTION_TIMEOUT_SECONDS=120

# 单个模型、RAG 或普通 Workflow 节点默认最多执行 30 秒。
FOODMATE_AGENT_NODE_TIMEOUT_SECONDS=30

# 等待用户补充、工具审批或预算确认的最长时间，默认 24 小时。
FOODMATE_AGENT_WAITING_USER_TIMEOUT_SECONDS=86400

# 用户取消后等待已提交 Tool/SQL 收敛的最长时间，默认 10 秒。
FOODMATE_AGENT_CANCEL_DRAIN_TIMEOUT_SECONDS=10
```

所有超时在 Run 开始时固化为 `TimeoutSnapshot`。节点可以声明更短 timeout，不能扩大 Runtime 上限；Java、Python 和下游调用统一使用绝对 deadline。

### 5.4 Token、成本与预算追加

```dotenv
# 单 Run 最大总 Token，包含 Router、Planner、Composer 和在线 LLM Eval。
FOODMATE_AGENT_MAX_TOKENS_PER_RUN=30000

# 单 Run 最大估算成本，单位人民币元；未知实际账单时必须标记 estimated=true。
FOODMATE_AGENT_MAX_COST_CNY_PER_RUN=0.50

# 达到预算 70% 后停止非必要 Reflection、减少可选检索并限制扩展任务。
FOODMATE_AGENT_BUDGET_SOFT_RATIO=0.70

# 达到预算 85% 后禁止重规划/重写，并允许低风险节点切换经济模型。
FOODMATE_AGENT_BUDGET_HARD_RATIO=0.85

# 达到 100% 后是否允许用户明确确认追加预算。
FOODMATE_AGENT_ALLOW_BUDGET_EXTENSION=true

# 每次用户确认最多追加 30000 Token。
FOODMATE_AGENT_MAX_TOKEN_EXTENSION_PER_CONFIRMATION=30000

# 每次用户确认最多追加 ¥1.00 估算成本。
FOODMATE_AGENT_MAX_COST_EXTENSION_CNY_PER_CONFIRMATION=1.00

# Runtime 全局日成本保险丝，单位人民币元；当日累计估算成本达到上限后，
# 准入直接拒绝新 Run，返回 RUNTIME_DAILY_BUDGET_EXCEEDED。
FOODMATE_AGENT_DAILY_COST_LIMIT_CNY=20.00

# Runtime 全局日 Token 保险丝；与日成本任一先触线即生效。
FOODMATE_AGENT_DAILY_TOKEN_LIMIT=2000000
```

当前不建设账户余额、租户配额或供应商余额查询。预算追加只取“用户本次明确授权”与“Runtime 单次追加上限”的较小值；每次追加生成新的 BudgetSnapshot revision、dispatch attempt 和审计记录。

日保险丝规则：

- 目的是保护开发者个人 API Key，防止循环缺陷或误操作在无人值守时持续烧钱；它不是用户配额体系，不做按用户拆分。
- 两个值必须大于 0，按 UTC 自然日重置；用量计数使用与单 Run 预算相同的估算口径，允许少量滞后但必须单调累加。
- 触线只拒绝**新 Run 准入**；已在执行的 Run 继续受各自 `RunBudgetSnapshot`、deadline 和取消控制，不被强制中断。
- 触线拒绝与预算追加确认无关：日保险丝触发后，用户级预算追加也不能绕过它。
- 该检查是确定性检查，位于 Redis 准入之前或之中执行，不调用模型。

### 5.5 模型路由与 Eval

```dotenv
# 复杂规划、关键 Composer 和高风险任务的模型别名；必须由部署环境填写。
FOODMATE_MODEL_TIER_HIGH=

# Router、抽取和普通问答的标准模型别名。
FOODMATE_MODEL_TIER_STANDARD=

# 预算紧张时低风险节点使用的经济模型别名。
FOODMATE_MODEL_TIER_ECONOMY=

# 在线 LLM Judge 使用的独立评测模型别名。
FOODMATE_MODEL_TIER_EVAL=

# 主模型发生 timeout、rate limit 或供应商故障时是否允许走兼容 fallback。
FOODMATE_MODEL_FALLBACK_ENABLED=true

# standard 主模型仅在 timeout、限流或供应商 5xx 时，才允许切换到 economy。
# schema、权限、安全和预算类错误不会触发 fallback。
FOODMATE_MODEL_FALLBACK_STANDARD=economy

# 是否启用在线 LLM Judge；确定性硬规则始终启用，不受此开关影响。
FOODMATE_AGENT_LLM_EVAL_ENABLED=true

# 低风险任务抽样执行 LLM Eval 的比例，0.20 表示 20%。
FOODMATE_AGENT_LLM_EVAL_SAMPLE_RATIO=0.20

# 高风险和复杂任务是否强制执行 LLM Eval。
FOODMATE_AGENT_LLM_EVAL_REQUIRED_FOR_HIGH_RISK=true

# 单次 LLM Eval 最长 15 秒。
FOODMATE_AGENT_LLM_EVAL_TIMEOUT_SECONDS=15

# LLM Eval 最低通过分数。
FOODMATE_AGENT_LLM_EVAL_PASS_SCORE=0.80

# 当前没有实际审核人员，必须保持 false。
FOODMATE_AGENT_HUMAN_REVIEW_ENABLED=false

# Eval 通过前禁止向前端发送候选答案正文；生产环境必须为 false。
FOODMATE_AGENT_STREAM_UNEVALUATED_CONTENT=false

# 候选答案服务端缓冲上限，默认 256 KiB。
FOODMATE_AGENT_ANSWER_BUFFER_MAX_BYTES=262144
```

模型层级值必须是 `provider_id:model_name`。未设置时，Runtime 为本地开发使用
`deterministic:local`，它不联网也不代表真实云模型已接入。生产或联调环境应显式填写
四个层级，并为实际使用的每个 `provider_id` 提供以下配置；`provider_id` 只能使用小写字母、数字、`_` 和 `-`，环境变量中将 `-` 写成 `_`。

```dotenv
# 两个独立云端点的示例。两者均需兼容 OpenAI Chat Completions 协议；密钥只能由部署环境注入。
FOODMATE_MODEL_TIER_HIGH=cloud_a:reasoning-model
FOODMATE_MODEL_TIER_STANDARD=cloud_a:chat-model
FOODMATE_MODEL_TIER_ECONOMY=cloud_b:cheap-chat-model
FOODMATE_MODEL_TIER_EVAL=cloud_b:judge-model

# provider_id=cloud_a 的连接、超时和估价配置。价格为每百万 Token 的人民币估算单价。
# 未完成价格表审计时必须留空，Runtime 会记录成本未知，不能填 0 伪造免费调用。
FOODMATE_MODEL_PROVIDER_CLOUD_A_BASE_URL=https://provider.example.test/v1
FOODMATE_MODEL_PROVIDER_CLOUD_A_API_KEY=
FOODMATE_MODEL_PROVIDER_CLOUD_A_TIMEOUT_SECONDS=30
FOODMATE_MODEL_PROVIDER_CLOUD_A_INPUT_CNY_PER_MILLION_TOKENS=
FOODMATE_MODEL_PROVIDER_CLOUD_A_OUTPUT_CNY_PER_MILLION_TOKENS=

# provider_id=cloud_b 的配置同理。价格未知时保持留空，Token 用量仍会记录，但成本字段为 unknown。

FOODMATE_MODEL_PROVIDER_CLOUD_B_OUTPUT_CNY_PER_MILLION_TOKENS=

# 价格配置的版本号会写入 Runtime Trace，便于之后回溯成本估算口径。
FOODMATE_MODEL_PRICE_VERSION=unconfigured
```

生产成本审计：将 `FOODMATE_MODEL_PRICE_AUDIT_REQUIRED=true` 后，云模型必须同时配置已审计的输入/输出单价和价格版本，否则 Runtime 会在发出云请求前返回 `MODEL_PRICE_UNCONFIGURED`。模型级配置优先于供应商级配置，DeepSeek-V4-Flash 的环境变量名示例为 `FOODMATE_MODEL_PROVIDER_CLOUD_PRIMARY_DEEPSEEK_AI_DEEPSEEK_V4_FLASH_*`。本地 `deterministic:local` 不受该开关影响。

DeepSeek-V4-Flash 若供应商响应携带 `usage.prompt_tokens_details.cached_tokens`，成本会把缓存命中输入单独计费。对应变量是 `FOODMATE_MODEL_PROVIDER_CLOUD_PRIMARY_DEEPSEEK_AI_DEEPSEEK_V4_FLASH_CACHED_INPUT_CNY_PER_MILLION_TOKENS`；未使用缓存时该字段不会影响成本。`run.model_usage.usage.cached_input_tokens`、`cost.amount` 和 `price_version` 一起保留在审计事件中。

当前适配器已支持多个 OpenAI 兼容云端点与确定性本地 provider；尚未为任何厂商写入密钥、默认地址或价格。`eval` 即使与回答模型属于同一供应商，也必须是一次独立调用并有独立 usage 记录。

模型别名为空时，对应能力 readiness 失败或按明确的可选能力降级，不能猜测供应商。高风险 `request_review` 在无人审核条件下进入安全降级，不创建虚假的人工审核等待状态。

### 5.8.2 结构化反馈业务入口（2026-08-23）

用户可通过 `POST /api/agent-runs/{runId}/messages/{messageId}/feedback` 对自己已完成 AgentRun 的 assistant 回答提交一次结构化反馈。请求必须携带 `Idempotency-Key`，支持 `helpful`、最多 6 个稳定原因代码和最多 1000 字符的补充说明；服务端会校验用户、Run 和 assistant message 的归属，不接受前端传入运行版本或其他审计字段。

反馈事实写入 `agent_feedback`，统一审计只保留反馈结果、原因数量、关联 ID、幂等键和参数摘要。回答正文、Prompt、原始请求、令牌和敏感说明不进入审计；`fabricated_execution` 与 `unsafe_or_privacy` 原因可按 `FOODMATE_AGENT_FEEDBACK_AUDIT_HIGH_RISK_ENABLED` 标记高优先级。V26 迁移、validation 和 rollback precheck 需要按数据库人工执行流程登记，当前代码测试不等同于已执行目标数据库迁移。

### 5.8.1 当前记忆与恢复实现状态（2026-07-29）

- `FOODMATE_AGENT_CONTEXT_MAX_RECENT_MESSAGES=8` 已作为实际短期记忆上限；第 9 条有效消息会触发结构化摘要更新。
- 长期记忆读取当前只装配已确认、未过期的白名单类型，Java 查询上限为 8；新的候选不再接受完整计划、一次性参数、营养目标和医疗事实。数据库仍保留历史 `plan`、`temporary/session_context` TTL 分支，仅用于兼容旧记录。
- Redis checkpoint 已使用 TTL、大小上限、CAS 和可选 Fernet 加密。恢复命令必须提供旧 dispatch、checkpoint version/digest、预算 revision、deadline 和已完成 invocation；Java 对账入口、新 dispatch attempt 和 Python 重启后的本地恢复闭环已经验证，生产自动触发器和恢复指标仍待完成。
- Eval 相关配置已进入 Runtime 主路径；本地 Golden、schema/provider fail-closed、安全降级和延迟统计已有回归，生产人工校准、统一指标和告警仍未完成。

### 5.9 RocketMQ、本地消息状态与回答分片

Python RocketMQ producer 和 consumer 都受启动超时保护。Proxy 不可用时返回 `RUNTIME_MQ_STARTUP_FAILED`，不会无限等待：

```dotenv
# Python RocketMQ Proxy route 查询的最大启动等待时间，单位秒。
FOODMATE_ROCKETMQ_STARTUP_TIMEOUT_SECONDS=15
```

```dotenv
# 本地正式异步传输模式；RocketMQ 基础 transport 已进入代码并完成真实往返验证。
FOODMATE_AGENT_TRANSPORT=rocketmq

# 本地单节点 RocketMQ NameServer 地址。
FOODMATE_ROCKETMQ_NAMESRV_ADDR=localhost:9876

# Java -> Python：RunCommand、CancelCommand。
FOODMATE_ROCKETMQ_TOPIC_AGENT_COMMAND=foodmate-agent-command-v1

# Python -> Java：RunEvent、RuntimeError。
FOODMATE_ROCKETMQ_TOPIC_AGENT_EVENT=foodmate-agent-event-v1

# Python -> Java：ToolProposal、SqlProposal。
FOODMATE_ROCKETMQ_TOPIC_AGENT_PROPOSAL=foodmate-agent-proposal-v1

# Java -> Python：ToolResult、SqlResult。
FOODMATE_ROCKETMQ_TOPIC_AGENT_RESULT=foodmate-agent-result-v1

# Java 消费 Agent 事件的消费组；同一环境必须稳定，不能每次启动随机生成。
FOODMATE_ROCKETMQ_CONSUMER_GROUP_JAVA_AGENT_EVENT=foodmate-java-agent-event-v1

# Java 消费 Tool/SQL Proposal 的消费组。
FOODMATE_ROCKETMQ_CONSUMER_GROUP_JAVA_AGENT_PROPOSAL=foodmate-java-agent-proposal-v1

# Python 消费 Run/Cancel Command 的消费组。
FOODMATE_ROCKETMQ_CONSUMER_GROUP_PYTHON_AGENT_COMMAND=foodmate-python-agent-command-v1

# Python 消费 Tool/SQL Result 的消费组。
FOODMATE_ROCKETMQ_CONSUMER_GROUP_PYTHON_AGENT_RESULT=foodmate-python-agent-result-v1

# 单次发送等待 Broker 确认的最长时间，单位毫秒。
FOODMATE_ROCKETMQ_SEND_TIMEOUT_MS=3000

# Producer Relay 发布失败后的最大重试次数；业务消息身份在重试中保持不变。
FOODMATE_ROCKETMQ_PRODUCER_MAX_RETRIES=3

# Consumer 单条消息处理超时，单位秒；不得超过请求级绝对 deadline。
FOODMATE_ROCKETMQ_CONSUME_TIMEOUT_SECONDS=60

# 消费失败进入 DLQ 前的最大重试次数；DLQ 不自动裁决 AgentRun 失败。
FOODMATE_ROCKETMQ_CONSUMER_MAX_RETRIES=8

# Python Redis MQ Inbox 和已发布 Outbox 的默认保留时间，单位天。
FOODMATE_AGENT_MQ_TECHNICAL_STATE_TTL_DAYS=7

# Python MQ 技术状态 Redis key 前缀。
FOODMATE_AGENT_MQ_REDIS_PREFIX=foodmate:agent:mq

# 回答分片事件之间的最长等待间隔，单位毫秒；当前 Runtime 默认 150ms，实际值受安全上限约束。
FOODMATE_AGENT_STREAM_CHUNK_INTERVAL_MS=150

# Eval 通过后单个回答分片最大字节数；Runtime 按 UTF-8 字节上限切分。
FOODMATE_AGENT_STREAM_CHUNK_MAX_BYTES=2048
```

本地阶段只使用单 NameServer + 单 Broker，不在本配置中假设生产集群、TLS 或 ACL。Topic 和 consumer group 属于契约化配置，不允许多个环境共享同一消费组。`FOODMATE_AGENT_TRANSPORT=http` 只用于 M1-3 兼容和契约测试；MQ 发布不确定时禁止自动回退 HTTP 双发。

配置规则：

1. 环境变量是部署配置来源，不允许在 Prompt、前端参数或用户消息中覆盖。
2. Runtime 启动时统一解析并校验；非法、负数或超出实现安全范围时 readiness 失败。
3. 接受 Run 时将有效值固化为 `RunBudgetSnapshot`；修改环境变量只影响新 Run。
4. 恢复旧 Run 必须读取 checkpoint 中的原快照，不能套用当前进程的新配置。
5. Java 可通过后续 RunCommand 策略收紧单 Run 预算，但不能扩大 Runtime 环境上限。
6. 次数预算不是唯一保护，仍必须同时执行 deadline、取消、token 和成本门禁。
7. 环境变量在 Runtime 启动时解析；变更后需要受控重启，只影响新 Run。
8. 比例必须满足 `0 < SOFT_RATIO < HARD_RATIO < 1`；计数、字节数和 timeout 必须位于实现允许范围。
9. 生产启动必须拒绝 `STREAM_UNEVALUATED_CONTENT=true` 和 `HUMAN_REVIEW_ENABLED=true`（除非后者已有独立 ADR 与审核能力门禁）。
10. Topic、consumer group、Redis namespace 和 transport mode 必须在启动时校验；同一进程不能同时启用 HTTP 与 MQ 业务派发。

## 6. 配置变更检查

修改当前 Java YAML 后，使用相应 profile 启动 Java，并检查 `/actuator/health`。对需要数据库的 profile，先确认环境变量和可用 PostgreSQL；`local-stub` 不验证数据库或未来 Runtime。目标双运行时配置落地后，再增加启动时的 HTTPS、契约版本、JWT TTL、`kid`、私钥引用和 timeout 校验，并在测试中验证不泄漏 secret。

### 6.1 M3 保留治理安全边界

当前 M3 保留治理没有新增可在环境变量中打开数据库硬删除的开关。数据库策略表中的 `hard_delete_enabled` 默认值为 `false`，必须由受控策略数据和独立审批流程共同决定；本地业务测试不会改变该值，也不会自动执行迁移、对象删除、向量删除或数据库删除。

本地验证只允许检查策略、legal hold、审批、任务依赖顺序、幂等和失败补偿。真实删除前必须另行准备备份/回滚证据、目标范围复核、真实依赖连接和删除演练记录；禁止将配置文件、启动成功或单元测试结果解释为已完成生产数据清理。
### M1-4 Runtime readiness 与 Eval 指标

Runtime 启动后使用 `GET /foodmate/internal/health/ready` 检查协调依赖。响应会列出 checkpoint backend、Redis、RocketMQ event/proposal producer、command/result consumer；任一生产所需依赖不可用时返回 HTTP `503`，错误码为 `RUNTIME_COORDINATION_UNAVAILABLE`，Java 不应继续向该实例派发新 Run。

Runtime readiness 同时返回当前进程内 Eval 统计：`pass_rate`、`degrade_rate`、`provider_failure_rate`、`schema_invalid_rate`、`p95_latency_ms` 和 `p99_latency_ms`。这些指标不保存 Prompt/答案，重启后重新计数；正式部署需要接入统一指标系统，不能把它们当作生产价格或账单事实。

默认模型仍是 `deterministic:local`。根目录 `.env` 若显式填写云模型 tier，才会发生云端调用；真实模型启用前仍必须完成价格版本和账单抽样对账。
