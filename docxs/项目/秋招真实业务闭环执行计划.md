# 秋招真实业务闭环执行计划

## 目标与完成口径

将 FoodMate 从“deterministic 本地业务闭环”推进到可在秋招面试中现场复现的“真实云模型完整闭环”。本计划只优先保证业务正确性，不把性能压测、长稳、组合故障、生产部署或生产容量作为完成门槛。

真实闭环必须满足：真实 Chat 模型实际参与意图识别、Proposal/SQL 生成和回答；真实 Embedding 实际参与知识检索；Java 仍是用户授权、确认、业务写入、SQL 执行和审计的唯一权威；失败不得静默回退到 deterministic。

固定配置：

- Chat：SiliconFlow OpenAI-compatible API，`deepseek-ai/DeepSeek-V4-Flash`。
- Embedding：SiliconFlow OpenAI-compatible `/embeddings`，`Qwen/Qwen3-Embedding-0.6B`。
- 向量库：Docker Compose Milvus，使用独立 collection。
- 执行账号：现有本地管理账号；测试数据使用时间戳命名空间，不触碰既有业务数据。
- 真实执行开关：必须显式 `--execute-paid` 或等价开关；普通 Maven、pytest、前端测试禁止调用云服务。
- 费用约束：最多 4 个真实场景，单轮不自动重试，整轮预算上限 5 CNY；超限立即 fail-closed。

截至 2026-09-06，R1、R2、R3、R4 均已取得一次真实云业务闭环证据：R1 覆盖真实 Embedding/Milvus 检索，R2 覆盖 `food_log_writer` 确认写入，R3 覆盖餐食计划确认保存，R4 覆盖只读 SQL Agent。以下性能、长稳、依赖故障和生产项仍不属于本计划当前完成门槛。

## 四条必须跑通的业务链路

### R1：真实 RAG 问答

管理员上传 3～5 份可公开展示来源的中文营养资料，包含来源名称、版本、许可说明和章节结构。流程为：

`管理员上传 -> MinIO -> Java 索引 Outbox -> RocketMQ -> Python 解析/分块 -> 真实 Embedding -> Milvus -> Java 结果回写 -> 显式发布 -> 用户提问 -> 检索 -> 真实 Chat 回答 -> run.completed/SSE 引用`

验收断言：文档只有发布且索引完成后可检索；引用包含标题、版本、章节、chunk ID 和安全片段；不包含对象地址、对象键、Prompt、API Key 或完整原文；无命中时不伪造引用；下线后同一查询不再返回该文档。

### R2：真实饮食记录写入

流程为：

`自然语言记录饮食 -> 真实 Chat 识别意图并生成 food_log_writer Proposal -> Java 校验用户/Run/参数/权限 -> 前端确认 -> Java 执行 PostgreSQL 写入 -> 营养匹配/分析 -> 审计 -> run.completed/SSE`

验收断言：Proposal 必须来自真实模型且符合结构化契约；未确认不得写库；拒绝不产生业务副作用；重复确认只产生一次副作用；写入、营养结果、审计和终态可按关联 ID 对账。

### R3：真实餐食计划

流程为：

`自然语言目标/忌口 -> 真实 Chat 生成结构化计划 -> Java/Tool Gateway 调用 plan_validator -> 返回问题/警告 -> 用户确认 -> Java 保存计划 -> 购物清单 -> 审计 -> SSE`

验收断言：过敏原、忌口、天数、餐次和预算约束有效；校验失败不得保存；确认后只由 Java 写入；计划和购物清单关联正确；重复提交幂等。

### R4：真实 SQL Agent

流程为：

`自然语言查询 -> 真实 Chat 生成结构化 SQL Proposal -> Java SQL AST Guard -> 当前用户过滤/白名单/只读/LIMIT/超时 -> PostgreSQL 执行 -> 脱敏结果与 SQL 审计 -> 真实 Chat 组织回答 -> SSE`

允许演示查询：近 7 天热量汇总、蛋白质摄入趋势、最近餐食计划。禁止写操作、跨用户查询、系统表、敏感字段和任意表访问。

验收断言：模型不能绕过 Java Policy；非法 SQL、跨用户条件、写语句和敏感字段均被拒绝并记录稳定错误码；合法查询只返回当前管理账号自己的白名单数据；SQL、结果、行数、耗时和审计可追溯。

## 执行阶段

### 阶段 0：凭据、预算和环境门禁

1. 在本地忽略的 `.env` 中分别配置 Docker Chat Key 和 Embedding Key，禁止混用。
2. 确认 Chat tier、Embedding profile、Milvus collection 和价格版本一致。
3. 用一次 Chat smoke 和一次 Embedding smoke 验证 HTTP 认证；失败时停止，不继续消耗额度。
4. 使用 `docker compose --env-file .env -f docker/compose.yml up -d --build --force-recreate foodmate agent-runtime` 启动应用。
5. 检查 Java 与 Python readiness；不得把 readiness 当成供应商调用成功。

阶段 0 最新执行证据（2026-09-05）：Docker Chat 路由已确认到 `cloud_primary:deepseek-ai/DeepSeek-V4-Flash`，Embedding 路由已确认到 `openai-compatible/Qwen/Qwen3-Embedding-0.6B`；`paid-cloud-preflight.ps1 -Scenario rag -ExecutePaid` 通过并启用最多 4 个场景、累计 5 CNY、无自动重试的付费门禁。随后 Chat smoke 返回 `23` tokens，Embedding smoke 返回 `1024` 维、`5` prompt tokens，Java/Python readiness 均通过。该轮未执行压测、故障矩阵或额外业务场景。

### 阶段 1：真实 RAG 数据准备与索引

1. 选择 3～5 份公开营养资料，记录来源、版本、许可说明和文件校验摘要。
2. 通过真实管理员 API 上传，确认批次和条目状态。
3. 等待 Java Outbox、RocketMQ、Python 解析、真实 Embedding、Milvus upsert 和 Java 结果回写完成。
4. 执行显式发布 API，核对 PostgreSQL 权威状态、visibility Outbox 和 Milvus metadata。
5. 执行 R1 查询，保存脱敏的请求、事件序号、模型/provider、引用摘要和数据库状态。

## 代码注释、规范与交付门禁

1. 适用于本计划新增或修改的生产代码、测试代码、迁移脚本、工具脚本和配置文件：Java、Python、TypeScript、TSX、JavaScript、SQL、PowerShell、Bash、YAML、Dockerfile、HTML 和 CSS 文件中的行注释、块注释、Javadoc、文档字符串、测试说明及配置说明统一使用中文。
2. 注释必须说明设计原因、权限/安全边界、失败处理、幂等约束或数据生命周期等代码不易直接表达的信息；不得用注释重复描述变量赋值、方法调用等表面行为，也不得用注释掩盖缺失的实现或测试。
3. 协议名称、类名、方法名、配置键、错误码、Topic、URL、第三方产品名和必要的英文技术术语可以保留原文；但围绕这些标识的自然语言说明必须使用中文。不得新增英文自然语言注释，也不得新增无意义的中英文双语重复注释。
4. 修改已有代码时只处理本次功能涉及的文件和代码区域，不进行无关的全仓库注释翻译；若本次改动区域存在过时、错误、与实现不一致或会误导使用者的英文注释，必须随代码一起改成准确的中文说明。
5. SQL 的 `COMMENT ON`、配置样例中的解释性注释和脚本帮助文本也遵循中文要求；第三方协议字段、官方命令和必须原样复制的供应商示例可保留英文，但要在相邻位置补充中文语义说明。
6. Java 代码遵循项目既定的 Java 21、构造函数注入、模块职责边界、Spotless 和 Alibaba Java 编码约束；Python、前端、SQL 和脚本沿用现有格式化、类型检查、异常处理和安全边界。测试代码、fixture、迁移 validation/rollback 和本地诊断脚本同样必须遵守中文注释要求。
7. 每完成一个可独立验收的大功能点，集中运行该功能点的业务测试和必要的格式/静态检查，核对实现、接口、迁移、配置、执行记录及相关说明后再提交；不为单个小方法或单个注释修改单独启动完整测试轮次。
8. 提交前检查本次 Git diff：逐个查看新增/修改的注释、Javadoc、文档字符串和配置说明是否为中文，扫描是否混入密钥、临时文件和测试数据，并确认代码、测试、文档和执行记录保持一致。发现不符合要求时，先修正再提交。
9. 中文注释属于功能交付定义的一部分，不单独为一个注释修改启动完整测试；但每个大功能点提交前必须完成注释语言复核，发现受影响区域的英文注释过时或会误导使用者时，必须在同一功能提交中修正。

## 测试与门禁

普通业务门禁：

- Java 受影响模块测试和 `mvnw.cmd verify`。
- `agent-runtime\\.venv\\Scripts\\python.exe -m pytest -q`。
- 前端 `npm.cmd run lint`、`npm.cmd run typecheck`、`npm.cmd test -- --run`、`npm.cmd run build`。
- Docker Compose 静态配置、Java/Python readiness 和本地依赖状态。

真实付费门禁：

- 仅显式命令触发，最多四个场景，单轮无自动重试，总费用不超过 5 CNY。
- 每条链路必须有真实 provider/model 证据，不能只看 `healthy`。
- 每条链路必须有业务状态、审计、消息关联和 SSE 终态断言。
- 任一模型超时、结构化输出不合规、Embedding 失败或 Eval 拒绝，均保留真实错误码并结束该场景，不自动回退 deterministic。
